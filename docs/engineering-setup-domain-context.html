A deep reading of two deceptively simple assumptions behind the engineering skills: run the setup skill first, and treat domain context as the shared language that makes agent work safe, compact, and cumulative.

The central idea: these skills are not independent tricks. They are a small operating system. /setup-matt-pocock-skills installs the wiring; CONTEXT.md and ADRs provide the memory; the other skills use that wiring and memory to avoid guessing.

The frame

These skills assume a repo can teach the agent how to behave.

A first-time user might expect each skill to contain everything it needs. But this repository is designed differently: the skills share a project-specific layer of instructions. That layer tells them where issues live, which labels mean what, where domain language is recorded, and which decisions should not be re-litigated.

Without setup, the agent asks: “What should I assume?”
With setup and context, it asks: “What does this project already know?”

Skills are workflows

They are not just tips. A skill like tdd or triage has a protocol: inspect, ask, write, label, test, or stop.

Setup is wiring

/setup-matt-pocock-skills writes the stable pointers other skills need so they do not rediscover local conventions every time.

Context is language

CONTEXT.md defines what project words mean, what synonyms to avoid, and how concepts relate.

Point one

Run setup first because it converts vague environment into explicit contract.

/setup-matt-pocock-skills is not a cosmetic welcome step. It is the bootstrap that answers three questions every serious engineering workflow eventually needs answered.

Where does work live?

The issue tracker may be GitHub, GitLab, local markdown, or another system. Skills that create or triage work need to know the destination before acting.

Where is memory?

The agent needs to know whether domain context is global, split by context, and where ADRs live.

What setup writes

It adds or updates an ## Agent skills block in CLAUDE.md or AGENTS.md, then writes:

  • docs/agents/issue-tracker.md
  • docs/agents/triage-labels.md
  • docs/agents/domain.md

What setup refuses to do

It is deliberately prompt-driven, not a blind script. It should inspect the repo, present findings, ask one decision at a time, show a draft, then write. That matters: setup is where the agent asks for authority instead of silently inventing conventions.

Point three

Domain context matters because names are compressed decisions.

A domain term is not merely a word. It is a boundary, a history, a set of allowed assumptions, and a warning against nearby wrong ideas. When the agent uses the right term, it inherits all of that. When it uses the wrong synonym, it may accidentally design the wrong thing.

Without domain context

  • The agent says “account” because it sounds plausible.
  • Issue titles drift between customer, user, client, account.
  • Tests describe implementation mechanics instead of business behavior.
  • Architecture reviews reopen decisions that were already settled.

With domain context

  • The agent distinguishes Customer from User.
  • Issues, tests, and PRDs share one vocabulary.
  • Relationships become explicit: one Order produces many Invoices.
  • ADRs explain why surprising decisions exist.

CONTEXT.md is a glossary plus a map

It records canonical terms, aliases to avoid, relationships, example dialogue, and flagged ambiguities. It should contain domain concepts, not general programming concepts.

ADRs are memory for non-obvious choices

An ADR is valuable when a decision is hard to reverse, surprising without context, and the result of a real trade-off. It prevents future agents and humans from “fixing” something that was deliberate.

# Context Name

## Language

**Order**:
A request by a Customer for goods or services.
_Avoid_: Purchase, transaction

## Relationships

- An **Order** produces one or more **Invoices**
- An **Invoice** belongs to exactly one **Customer**

## Flagged ambiguities

- "account" was used to mean both **Customer** and **User** — resolved: these are distinct concepts.
How context begins

CONTEXT.md is populated lazily, then sharpened whenever confusion becomes knowledge.

Setup does not fill CONTEXT.md with placeholder prose. That restraint is intentional. A context file earns its existence when a real term, relationship, or ambiguity has been resolved.

A fuzzy word appears

Someone says “account,” “subscription,” “workspace,” “job,” or another word that could mean more than one thing.

The agent interrogates it

/grill-with-docs asks one question at a time, checks the code when code can answer, and challenges contradictions with existing glossary terms.

The team resolves the meaning

The answer becomes explicit: for example, Customer is the paying entity, while User is a login identity.

The file is updated immediately

The resolved term, aliases to avoid, relationships, and flagged ambiguity are captured in CONTEXT.md while the understanding is still fresh.

Healthy evolution

  • More precise definitions.
  • Fewer ambiguous synonyms.
  • Clearer relationships and cardinality.
  • Example dialogue that demonstrates boundaries.

Unhealthy evolution

  • A giant wiki of everything.
  • Implementation notes disguised as domain language.
  • Stale terms that no one uses.
  • Requirements, changelog entries, or plans dumped into the glossary.
Setup points to the library. /grill-with-docs writes the dictionary. The other skills read it.
A separate vocabulary

LANGUAGE.md is not project memory. It is the architecture skill’s own dictionary.

The file skills/engineering/improve-codebase-architecture/LANGUAGE.md is bundled with that skill. It is not created by setup, not created by invoking the skill, and not normally improved by successive runs. It supplies stable architecture terms: Module, Interface, Seam, Adapter, Depth, Leverage, and Locality.

CONTEXT.md

  • Belongs to the project being worked on.
  • May be created lazily.
  • Improves over time as terms are resolved.
  • Names domain concepts like Order, Customer, Invoice.

LANGUAGE.md

  • Belongs to the architecture skill package.
  • Already exists in the repository.
  • Is treated as stable skill vocabulary.
  • Names architecture concepts like Module, Interface, Seam.
improve-codebase-architecture
  ├─ reads LANGUAGE.md
  │   └─ architecture vocabulary shipped with the skill
  ├─ reads CONTEXT.md / CONTEXT-MAP.md
  │   └─ project vocabulary discovered through setup's domain rules
  └─ reads docs/adr/

A strong architecture sentence combines both vocabularies: “The Order intake module has a shallow interface; moving validation behind the same seam would improve locality.” Order comes from project context. The rest comes from the skill’s architecture language.

The relation

Setup tells skills where context lives; context tells skills what reality means.

Setup establishes routes

It points to issue tracker rules, label vocabulary, and domain-doc consumer rules.

Domain docs establish language

They define what terms mean, what synonyms to avoid, which relationships matter, and which decisions carry history.

Producer skills improve the memory

grill-with-docs updates CONTEXT.md inline as terms resolve and offers ADRs only when the decision deserves permanence.

Consumer skills reuse the memory

diagnose, tdd, to-prd, to-issues, triage, zoom-out, and architecture work read the same vocabulary and decisions before producing output.

Consequential thinking

The cost of skipping these steps is not inconvenience. It is drift.

If you skip setup

  • Issue-producing skills may not know whether to call gh, glab, write markdown, or ask.
  • Triage may create duplicate labels or apply labels with the wrong meaning.
  • The agent repeatedly spends attention rediscovering conventions.
  • Workflows lose their shared assumptions and become ad hoc prompts.

If you skip domain context

  • PRDs, issues, tests, and architecture notes use inconsistent names.
  • Ambiguous words remain ambiguous, so decisions appear settled when they are not.
  • Agents contradict ADRs or reopen past trade-offs by accident.
  • The project accumulates AI prose instead of project knowledge.
Good setup reduces operational uncertainty. Good context reduces semantic uncertainty. You need both.
Standalone potential

Some skills can work before setup; workflow-writing skills should not have to guess.

The setup dependency is not equally strong everywhere. Skills that operate on code or conversation can often stand alone. Skills that publish, label, or triage work depend on repo workflow configuration.

Strong standalone

  • prototype: throwaway code to answer a question.
  • grill-with-docs: can create context lazily.
  • setup-matt-pocock-skills: the bootstrap itself.

Usable, but degraded

  • diagnose: can debug, but may lack domain language.
  • tdd: can test behavior, but names improve with context.
  • zoom-out: can map code, but context improves the map.
  • improve-codebase-architecture: has LANGUAGE.md, but wants CONTEXT.md and ADRs.

Setup strongly recommended

  • to-prd: wants labels and domain language.
  • to-issues: needs tracker destination and publishing conventions.
  • triage: public issue state changes should not be improvised.
Owning it

How to use this proficiently, not ceremonially.

When entering a new repo

  • Run /setup-matt-pocock-skills.
  • Answer the three setup questions with real project behavior, not aspirational behavior.
  • Prefer editing existing CLAUDE.md or AGENTS.md over creating competing instruction files.
  • Keep generated pointers concise; put detail in docs/agents/*.md.

When discussing product or architecture

  • Use /grill-with-docs when terms are fuzzy or plans need stress-testing.
  • Let the agent inspect code when code can answer a question.
  • Capture resolved terms immediately in CONTEXT.md.
  • Create ADRs sparingly: only for hard-to-reverse, surprising, trade-off decisions.

When writing issues, tests, or PRDs

  • Use glossary vocabulary in titles and acceptance criteria.
  • Prefer business behavior over implementation trivia.
  • Flag missing terms as a context gap, not as a reason to invent synonyms.
  • Make vertical slices that a future agent can pick up without hidden context.

When maintaining context

  • Delete stale terms; stale context is worse than absent context.
  • Record aliases to avoid, not just preferred words.
  • Use example dialogue to reveal boundaries between concepts.
  • Review ADRs before changing architectural direction.
